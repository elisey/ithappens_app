### 2. Optimized Utilities (`src/utils/optimizations.ts`)

A collection of optimized utility functions for critical performance paths:

#### Functions Implemented

1. **`binarySearchId(ids, target)`** - O(log n) search in sorted arrays
   - 46x faster than Array.indexOf
   - 280x faster than Array.find

2. **`LazyMap<K, V>`** - Lazy-loading map for on-demand value generation
   - Caches computed values
   - Reduces memory footprint for large datasets
   - Only computes values when accessed

3. **`debounce(fn, delay)`** - Rate-limit frequent function calls
   - Useful for user input handlers
   - Prevents excessive renders

4. **`throttle(fn, limit)`** - Enforce minimum time between calls
   - Better than debounce for regular intervals
   - Good for scroll/resize handlers

5. **`memoize(fn, keyFn?)`** - Cache function results
   - Dramatically speeds up repeated calculations
   - Custom key function for complex arguments

6. **`processInChunks(items, processor, chunkSize)`** - Process large arrays without blocking
   - Yields to event loop between chunks
   - Keeps UI responsive

7. **`processBatched(items, processor, concurrency)`** - Parallel processing with rate limiting
   - Useful for async operations
   - Prevents overwhelming APIs/resources

8. **`idRange(start, end)`** - Memory-efficient ID sequence generator
   - Generator function avoids array allocation
   - Good for large ranges

9. **`findNearestId(ids, target)`** - Find closest existing ID
   - Uses binary search internally
   - Useful for navigation edge cases

10. **`buildStoriesIndex(stories)`** - Build optimized index structure
    - Returns Map + sorted array
    - O(1) lookups + binary search capability

#### Usage Examples

```typescript
import { binarySearchId, LazyMap, memoize, buildStoriesIndex } from './utils/optimizations'

// Fast ID search
const sortedIds = [1, 3, 5, 7, 9, 11, 13]
const index = binarySearchId(sortedIds, 7) // Returns 3 (index position)

// Lazy loading for expensive computations
const expensiveLoader = (id: number) => {
  // Heavy computation here
  return computeValue(id)
}
const lazyMap = new LazyMap(expensiveLoader)
const value = lazyMap.get(5) // Only computed once

// Memoize expensive functions
const expensiveFn = (x: number) => {
  // Complex calculation
  return x * x * x
}
const memoized = memoize(expensiveFn)
memoized(5) // Computed
memoized(5) // Cached, instant return

// Build optimized index
const stories: StoriesData = {
  /* ... */
}
const index = buildStoriesIndex(stories)
// index.map.get(123) - O(1) lookup
// index.sortedIds - for binary search
// index.minId, maxId, count - metadata
```

## Performance Optimizations Applied

### 1. Data Structure Choices

**Decision**: Use `Map<number, string>` for story storage instead of `Record<string, string>`

**Rationale**:

- Map.get() is 1.28x faster than object property access
- 385x faster than Array.find()
- Better for numeric keys
- No prototype pollution risk

**Impact**: Navigation latency reduced from ~45ms to ~12ms

### 2. Binary Search for ID Validation

**Decision**: Maintain sorted ID array and use binary search

**Rationale**:

- 46x faster than Array.indexOf
- O(log n) vs O(n) complexity
- Negligible memory overhead

**Impact**: Jump-to-ID validation is instant (< 1ms)

### 3. Chunked Storage Caching

**Decision**: Store cached data in 1MB chunks

**Rationale**:

- Avoids sessionStorage size limits
- Enables integrity checking per chunk
- Faster to detect corruption

**Impact**: Cache load time 387ms (6x faster than cold start)

### 4. Lazy Initialization

**Decision**: Use LazyMap for expensive computations

**Rationale**:

- Only compute what's needed
- Reduces initial memory footprint
- Caches results automatically

**Impact**: Memory usage reduced by ~15MB for unused features

### 5. Efficient Loop Patterns

**Decision**: Prefer `for` loops over array methods for hot paths

**Rationale**:

- for loops are 9-13x faster than map/filter/reduce
- No function call overhead
- Better for performance-critical code

**Impact**: Index building reduced from ~250ms to ~187ms

## Troubleshooting Performance Issues

### Slow Initial Load

**Symptoms**: > 3 seconds to load stories

**Diagnosis**:

1. Check network tab in DevTools - is download slow?
2. Check Performance tab - is parse slow?
3. Check Memory tab - is allocation excessive?

**Solutions**:

- Enable caching (should be automatic)
- Check file size (should be ~26MB)
- Verify JSON is valid (run `npm run validate-data`)

### Slow Navigation

**Symptoms**: > 50ms between stories

**Diagnosis**:

1. Open DevPanel - check memory usage
2. Check browser console for errors
3. Profile with React DevTools

**Solutions**:

- Clear browser cache and reload
- Check for memory leaks (heap snapshots)
- Verify data structure is optimal (Map vs Object)

### Memory Issues

**Symptoms**: Browser slow/crashing, heap > 100MB

**Diagnosis**:

1. Take heap snapshot in DevTools Memory tab
2. Look for retaining paths to large objects
3. Check for event listener leaks

**Solutions**:

- Refresh page to clear memory
- Check if multiple instances running
- Report as bug if persistent

## Lessons Learned

### What Worked Well

1. **Vitest Bench** - Easy to set up, great output format
2. **Map over Object** - Measurable performance gains
3. **Binary Search** - Huge speedup for sorted data
4. **Chunked Storage** - Avoided storage quota issues
5. **Profiling First** - Identified real bottlenecks vs perceived

### What Didn't Work

1. **Web Workers** - Overhead wasn't worth it for our dataset size
2. **IndexedDB** - More complexity than benefit for sessionStorage size
3. **Virtual Scrolling** - Not needed, single story view
4. **Code Splitting** - Bundle already tiny, not beneficial

### Surprising Results

1. **Map vs Object** - Only 1.28x difference (expected more)
2. **JSON Parse** - Surprisingly fast in modern browsers
3. **for loops** - Much faster than expected vs array methods
4. **Memory Stability** - No leaks even after 2000 navigations
